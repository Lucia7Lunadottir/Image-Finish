# Архитектура image-finish — карта для чтения кода

Этот файл не пересказывает код, а отвечает на вопрос «куда смотреть». Написан по факту чтения ключевых файлов в сентябре 2026.

## 1. Точка входа и порядок запуска

`main.py` — вот и всё, с чего всё начинается:

1. Настраивает GL-контекст (`_configure_gl_surface`) — должно случиться **до** создания `QApplication`, иначе холст рисуется не тем OpenGL-профилем.
2. Создаёт `QApplication`, вешает `install_excepthook` (`core/app_logging.py`) — без этого необработанное исключение в любом слоте валит весь процесс (PyQt6 делает `abort()`, не просто печатает traceback).
3. Показывает сплэш, грузит шрифты/кисти/паттерны из `fonts/`, `brushes/`, `patterns/`.
4. Импортирует и создаёт `ui.main_window.MainWindow` — тут начинается тяжёлая часть.
5. Если в аргументах командной строки есть путь к файлу — открывает его.

`MainWindow.__init__` (`ui/main_window.py`) делает, по порядку:
- строит реестр из ~50 инструментов (`_build_tool_registry`, там же вверху файла) — каждый инструмент это отдельный класс из `tools/`;
- собирает UI (`_build_ui`): статус-бар, панель опций инструмента, `ToolBar` слева, вкладки документов справа, `PanelManager` (доки);
- восстанавливает раскладку окна (`ui/workspace.py`);
- подключает сигналы всех панелей к своим обработчикам (`_wire_signals` — самый длинный кусок кода в файле, но по сути просто таблица «сигнал панели → метод»);
- активирует инструмент «Brush» по умолчанию.

Ни один документ (изображение) при старте не создаётся — вместо холста показывается `WelcomePanel`, пока пользователь не нажмёт «Создать»/«Открыть».

## 2. Кто за что отвечает (по папкам)

- **`core/`** — данные и бизнес-логика, без единого импорта из `ui/` (кроме пары мест, где `document.py` лениво зовёт функции применения adjustment-эффектов из `ui/adjustments_dialog.py` — да, зависимость идёт и в обратную сторону, см. раздел 3). Ключевые файлы: `document.py` (модель документа/слоёв и композитинг), `layer.py` (классы слоёв), `history.py` (undo/redo), `pixel_buffer.py` (доступ к пикселям QImage как numpy-массиву без копирования), `serialization.py` (формат `.imfn`), `adjustments/` и `filters/` (математика конкретных эффектов).
- **`ui/`** — всё, что рисует окна: `main_window.py` (главное окно + примеси-actions), панели (`*_panel.py`), диалоги (`*_dialog.py`), `canvas_widget.py` (сам холст, приём мыши), `toolbar.py`, `panel_manager.py` (доки).
- **`tools/`** — классы инструментов (кисть, лассо, перо и т.д.), каждый наследует `base_tool.BaseTool` и реализует `on_press/on_move/on_release`. Инструменты не знают про Qt-виджеты — им дают `doc`, `pos`, цвета, опции, и они правят пиксели `core`-объектов напрямую.
- **`utils/`** — мелкие независимые от остального приложения помощники (`new_document_dialog.py`, `qimage_numpy.py`). Меньше связей, чем в остальных папках.
- **`tests/`** — pytest, без pytest-qt (своя фикстура `qapp` в `conftest.py`). Запуск: `QT_QPA_PLATFORM=offscreen python -m pytest tests/`.

## 3. Главные «узлы» — почему кажется, что «всё на всё ссылается»

Это не иллюзия и не случайность — у приложения реально есть 3-4 файла-хаба, через которые обязано пройти почти любое действие:

- **`ui/main_window.py` (1620 строк) — главный хаб.** `MainWindow` собран из 7 mixin-классов (`ui/actions/file_actions.py`, `edit_actions.py`, `layer_actions.py`, `image_actions.py`, `adjustment_actions.py`, `filter_actions.py`, `panel_actions.py`) — это **не** 7 независимых систем, это один класс `MainWindow`, просто его код физически лежит в разных файлах, чтобы 1620+ строк не были одним файлом на 5000 строк. Каждый пункт меню и почти каждый сигнал панели в итоге дёргает метод где-то в этих mixin'ах. Если ищете «что происходит по нажатию пункта меню X» — смотрите `ui/menu_builder.py` (какой метод привязан к пункту), а сам метод почти наверняка в одном из `ui/actions/*.py`.
- **`core/document.py` (717 строк) — модель, которую трогает вообще всё.** `Document` хранит список слоёв и умеет их композитить в одну картинку (`get_composite`/`_render_composite`). Инструменты пишут пиксели прямо в `layer.image`, UI дёргает `document.invalidate_composite()` и просит перерисовку, история (`core/history.py`) снимает и восстанавливает снимки слоёв документа. Три независимые системы (tools, ui, core.history) сходятся здесь.
- **`ui/canvas_widget.py` (1515 строк) — единственная точка входа мыши.** `CanvasWidget.mousePressEvent/mouseMoveEvent/mouseReleaseEvent` переводят экранные координаты в координаты документа и зовут `self.active_tool.on_press/on_move/on_release(doc_pos, document, fg, bg, opts)`. Это единственное место, где «мышь» превращается в «вызов метода инструмента» — поэтому у canvas так много связей и с `tools/`, и с `core/document.py`, и с оверлеями (`ui/overlay_renderers.py`, `ui/shape_scene_overlay.py`, `ui/text_edit_overlay.py`).
- **Обратная зависимость core → ui.** `core/document.py::_apply_layer_adjustment` импортирует функции применения эффектов из `ui/adjustments_dialog.py`, `ui/levels_dialog.py`, `ui/more_adjustments.py` (для рендера adjustment-слоёв). Формально это нарушает «core не знает про ui», но сделано осознанно: сами формулы применения эффекта (apply_curves, apply_levels...) живут либо в `core/adjustments/`, либо рядом с диалогом, который их же использует для live-превью — так не пришлось бы держать две копии одной формулы. Если ищете «как считается конкретный adjustment» — смотрите сначала `core/document.py::_apply_layer_adjustment`, он скажет, в каком именно файле формула.

Итог: то, что вы читаете как «система A ссылается на систему B, которая на C» — это в основном одна и та же цепочка **canvas → active_tool → document → history/ui-refresh**, просто она проходит буквально через каждую фичу, потому что в редакторе изображений почти любое действие меняет пиксели документа.

## 4. Как данные текут при обычном действии

### Мазок кистью
1. `ui/toolbar.py` — клик по иконке кисти эмиттит `tool_selected`, поймано в `MainWindow._wire_signals` → `self._toolbar.tool_selected.connect(self._activate_tool)`.
2. `MainWindow._activate_tool("Brush")` берёт готовый экземпляр `BrushTool` из `self._tools` (словарь, построенный один раз при старте) и присваивает его `canvas.active_tool` для каждой открытой вкладки.
3. Пользователь жмёт мышь на холсте → `CanvasWidget.mousePressEvent` (`ui/canvas_widget.py:969`) переводит координаты в document-space, **сохраняет pre-stroke снимок** (`_pre_stroke_state`, на будущее undo) и зовёт `active_tool.on_press(...)`.
4. `BrushTool.on_press/on_move` (`tools/brush_tool.py`) рисует пиксели прямо в `layer.image`, используя `core/pixel_buffer.py` для доступа к пикселям как к numpy-массиву без копирования.
5. Каждое движение мыши шлёт `pixels_changed` → `MainWindow._on_pixels_changed` (лёгкое обновление статус-бара, тяжёлые панели типа гистограммы **не** обновляются на каждый пиксель — иначе просадка FPS).
6. Отпускание кнопки → `mouseReleaseEvent` шлёт `document_changed` → `MainWindow._on_doc_changed`: вот тут `self._history.push(pre_stroke_state)` реально кладёт снимок в undo-стек (`core/history.py`), и через `QTimer.singleShot` с задержкой обновляются тяжёлые панели (слои, гистограмма, навигатор).

### Диалог adjustment (например, Curves) с живым превью
1. Пункт меню → `AdjustmentActionsMixin._curves()` (`ui/actions/adjustment_actions.py`) → `_show_adj_dialog(CurvesDialog, ...)`.
2. `_show_adj_dialog` сначала пушит pre-состояние в историю (`self._push_history`), **потом** открывает диалог — то есть отмена в диалоге не оставляет мусора в undo.
3. `CurvesDialog` наследует `_AdjustDialog` (`ui/adjustments_dialog.py:238`) — общий базовый класс для диалогов, которые **пишут прямо в `layer.image` документа** и просят перерисовать главный холст (в отличие от диалогов фильтров, у которых своё изолированное превью — см. ниже). При открытии `_AdjustDialog` копирует `layer.image`, и если изображение больше 1600px по длинной стороне — уменьшает копию (`downscale_for_live_preview`) специально для отзывчивости слайдеров.
4. Каждое движение слайдера — debounce 40 мс (`QTimer`) → `_apply_preview()` пересчитывает эффект на (возможно уменьшенной) копии и пишет результат в `layer.image`, зовёт `self._canvas_refresh` (на самом деле перехваченный `_on_refresh_requested`, который сначала до-масштабирует картинку обратно к полному размеру документа, **иначе слой на холсте визуально бы уменьшился** во время перетаскивания слайдера).
5. `OK` → полный пересчёт на настоящем полном разрешении (может уйти в фоновый поток с прогресс-баром для больших изображений), финальный `canvas_refresh`.

Второе, архитектурно отдельное семейство диалогов — фильтры (`ui/preview_canvas_base.py`, `PreviewCanvasBase`): Noise, Stylize, Sharpen, Pixelate, Blur Gallery и т.д. У них **своя изолированная зумируемая превью-панель** (не главный холст), поэтому нет нужды в трюке «расширить превью обратно» — на реальный документ они пишут только один раз, при принятии диалога. Если чините живое превью — сначала определите, в каком из двух семейств баг: у `_AdjustDialog` пишет в document-слой напрямую, у `PreviewCanvasBase` — рисует в отдельный виджет.

## 5. Шпаргалка «хочу сделать X — начни здесь»

- **Добавить новый инструмент** → создать класс в `tools/` (наследник `tools/base_tool.py::BaseTool`, реализовать `on_press`/`on_move`/`on_release`) → зарегистрировать в `_build_tool_registry()` (`ui/main_window.py`, самый верх файла) → добавить кнопку в `ui/toolbar.py` (там же таблица `_ToolDef` с иконкой/шорткатом) → при необходимости — страницу опций в `ui/tool_options/`.
- **Добавить новую панель (док)** → создать `ui/<name>_panel.py` → добавить в `PanelManager.PANEL_DEFS` (`ui/panel_manager.py:22`) → подключить её сигналы в `MainWindow._build_ui` (`ui/main_window.py`, там же, где подключены остальные панели, в районе `# Connect panel signals`).
- **Добавить adjustment с живым превью, который правит слой документа** → см. семейство `_AdjustDialog` в `ui/adjustments_dialog.py:238`; сама формула эффекта либо там же, либо в `core/adjustments/<name>.py`; пункт меню — в `ui/actions/adjustment_actions.py`; регистрация формулы для рендера adjustment-слоя — `core/document.py::_apply_layer_adjustment`.
- **Добавить фильтр с изолированным превью-окном** → см. `ui/preview_canvas_base.py::PreviewCanvasBase`; пункт меню — в `ui/actions/filter_actions.py`; формула — обычно в `core/filters/`.
- **Поменять формат сохранения `.imfn`** → `core/serialization.py`. Чтение старого формата (gzip+pickle) идёт через `LegacyPickleSerializer`, только на чтение — новый формат всегда ZIP(manifest.json + PNG-слои).
- **Поправить рендер композита слоёв (как слои складываются в одну картинку)** → `core/document.py::_render_composite` и `_render_layer_list` — сам перебор идёт через `layer.render_into(ctx, ...)`, то есть поведение конкретного типа слоя (обычный/группа/artboard/adjustment) смотрите в `core/layer.py`, в переопределении `render_into` нужного класса.
- **Добавить пункт меню / новое действие** → сам пункт меню — `ui/menu_builder.py`; обработчик — один из `ui/actions/*.py` mixin'ов, в зависимости от смысла (файл/правка/слой/изображение/adjustment/фильтр/панель); если действие меняет пиксели — не забыть `self._push_history(...)` **до** изменения.
- **Undo не работает / глючит** → `core/history.py` (сам стек) + место, где вызывается `self._push_history()`/`self._make_history_state()` (`ui/main_window.py`) — важно, что снимок обязан сниматься **до**, а не после мутации пикселей (см. комментарий в `Document.snapshot_layers`).

## Что осталось не до конца ясным

- `core/layer.py` (837 строк) прочитан только по публичному интерфейсу через вызовы из `document.py` — если понадобится редактировать сам класс `Layer`/`RasterLayer`/`VectorLayer`/`TextLayer` и их `render_into`, стоит прочитать файл отдельно и подробно, здесь этого разбора нет.
- `ui/canvas_widget.py` прочитан выборочно (первые ~120 строк + grep по обработчикам мыши); полный путь того, как оверлеи (`shape_scene_overlay.py`, `text_edit_overlay.py`) встраиваются в `paintGL`, разобран не был.
